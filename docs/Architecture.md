# Архитектура и границы

## Реализовано: baseline-v1

Файл → полная валидация → сутки МСК → совпадение бренда → точные дубли → тональность/важность → top-N → JSON и текст. Исходный код: [core.py](../src/cloud_digest/core.py).

- Прямой бренд: Cloud.ru с границами, исключающими часть другого слова/домена. Исторические кандидаты: SberCloud/Сберклауд, всегда ручная проверка; это гипотеза связи, не подтверждение актуальной принадлежности.
- Дубли: равенство полного текста после casefold и схлопывания пробелов. Кластер — SHA256; представитель — самое раннее время UTC, затем ID. Семантической кластеризации нет.
- Negative: подстроки `сбой`, `недоступ`, `утечк`, `авари`; positive: `спасибо`, `отличн`, `удобн`; иначе neutral. При обоих наборах negative и ручная проверка. Отрицания и сарказм не распознаются.
- Важность: +40 negative, +30 за кризисный маркер (`недоступ`, `утечк`, `авари`), +20 audience ≥10000, +10 views ≥1000. Максимум 100; неизвестные метрики не получают бонуса. Это выбранные эвристики, не обученная модель.
- Отбор сначала по важности, времени UTC и ID; показ выбранных карточек: negative → neutral → positive, внутри тот же порядок. Риск учитывает всех кандидатов дня, включая исключённых из top-N.
- `summary_160_300` фактически содержит первые 300 символов текста. Короткий текст не дополняется: менее 160 символов означает ручную проверку. Это выдержка, не сгенерированный пересказ.
- Ручная проверка: историческое имя, смешанная тональность, расхождение с BA, короткий текст, кризис; непустой `ba_topic_hit` без найденного бренда идёт только в очередь. Confidence 0.4 при причинах проверки, иначе 0.8 — техническая эвристика, не калиброванная вероятность. `escalate_pr`/`watch` — подсказки, автоматических действий нет.

## Целевой контур (ещё не реализован)

Brand Analytics — единственный внешний источник упоминаний. После приёма все данные, обработка, хранение, инференс моделей и редакторский процесс остаются на собственных ресурсах Cloud.ru:

BA → внутренний приём/валидация → внутреннее хранилище → правила и внутренний model endpoint → отбор/очередь редактора → дайджест.

Нужны внутренние планировщик, IAM, журналирование, мониторинг, сроки хранения и контроль версий правил/модели. Точный стек и мощности компании неизвестны; self-hosted модель и открытые библиотеки — предложения, не подтверждённые сервисы. Внешние LLM API не входят в целевой вариант. GitHub служит совместной разработке, не хранению или обработке производственных данных.

## Предлагаемый внутренний LLM-контракт

Адаптер и перечисленные ниже защиты пока не реализованы. Передаваемые поля ограничить allowlist: обезличенный `text`, проверенный `brand_context`, `task`, `schema_version`. Авторские name/ID, URL, секреты, лишние метаданные исключать; обезличивание текста проверять отдельно. Сопоставление ответа с исходным ID хранить внутри приложения, вне промпта.

Входной текст считать недоверенными данными, не инструкциями. Модель получает задачу определения связи/тональности и извлечения подтверждённых фрагментов; структурированный ответ: `brand_link`, `sentiment`, `matched_span`, `summary`, `confidence`, `human_review_needed`, `reasons`. Нужны валидация схемы/enum/длины, проверка цитат, чисел и имён по исходному тексту, запрет добавлять отсутствующие факты и обязательное решение редактора в спорных случаях. При таймауте, отказе или невалидном ответе — очередь ручной проверки с причиной, без выдуманного результата. Проверка наличия слов сама по себе не доказывает достоверность пересказа; редактор остаётся необходимым.
